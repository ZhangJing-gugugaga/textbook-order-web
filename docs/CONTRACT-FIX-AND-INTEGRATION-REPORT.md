## 二、问题清单与处置（按优先级）

### P0-1 · 审核必须回传 `contentVersion`（交接 A1）

| 项       | 内容                                                                                                                                                                                                                                                                                                                                             |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 根因     | 审核接口以 `contentVersion` 做 CAS。前端 `reviewApi.review` 只发 `{action, reason}`，服务端降级为「仅拦请求处理窗口内的并发提交」，**跨请求的重提拦不住**：管理员打开审核页 → 教师重提（状态仍是 `pending_review`，明细已被整单覆盖）→ 管理员点通过，审批结论落在没看过的内容上。                                                                |
| 修复     | `src/types/index.ts` 给 `OrderForm` 补 `contentVersion`；`src/api/orderForm.ts` 把 `contentVersion` 改为**必传**；`src/views/admin/ReviewView.vue` 新增 `runReview()` 统一带上详情读到的版本号，并在 409 `STATE_CONFLICT` 时**重新拉详情**让管理员重新确认（**不自动重试**——自动重试等于替他确认了没看过的内容）。详情弹窗新增「内容版本」展示。 |
| 测试结论 | ✅ 场景 A1 实测：首次提交 `contentVersion=36` → 教师重提 → 版本 37 → 用 36 审核 **409**「表单内容已变更或状态已更新，请刷新后重试」→ 用 37 审核 **200**。CAS 生效。                                                                                                                                                                              |
| 遗留风险 | 无。版本号缺失时前端**拒绝提交**（fail-closed），不会退回降级行为。                                                                                                                                                                                                                                                                              |

### P0-2 · 首登阶段禁止 `switch-role`（交接 A2）

| 项       | 内容                                                                                                                                                                                                                                                                                                            |
| -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 根因     | 后端首登放行清单从 `/api/auth/` 前缀通配改为**显式枚举**，`POST /api/auth/switch-role` 不再放行（它会重发 access/refresh，等于让未完成首登的会话拿到新的长效令牌）。而前端把「切换身份」入口放在 `DefaultLayout` 头部与个人中心，**首登强制跳转的落地页正是个人中心**——该入口在首登阶段可见可点，点了必然 403。 |
| 修复     | 三层防护：`src/stores/auth.ts` 的 `switchRole` 前置拦截（首登未完成直接抛 `FIRST_LOGIN_REQUIRED`，不发这个必然失败的请求）；`src/layouts/DefaultLayout.vue` 新增 `canSwitchRole`（首登阶段只隐藏切换动作，保留身份标签）；`src/views/profile/ProfileView.vue` 同样收敛。                                        |
| 测试结论 | ✅ 场景 A2 实测：首登待改密会话调 `switch-role` → **403 `FIRST_LOGIN_REQUIRED`**；`/api/me`（放行清单内）→ 200；`/api/admin/college`（清单外）→ 403。单测 `tests/unit/auth-store.spec.ts` 固化「首登中拒绝且不发请求 / 首登后可切换」。                                                                         |
| 遗留风险 | 无。                                                                                                                                                                                                                                                                                                            |

### P0-3 · 通知按 `target_roles` 定向，空队列是正常态（交接 A3）

| 项       | 内容                                                                                                                                                                                                                                                                                         |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 根因     | `/notice/unconfirmed`、`/notice/mine`、`/notice/{id}/confirm` 三处都只对**面向本人角色**的任务生效（ADMIN 全量）。供货商不在窗口变更通知的 `target_roles` 内 → 其队列**恒为空**，属预期而非故障。另外 `confirm` 对不在定向范围内的任务返回 **404**，原实现会把它当可重试错误，弹窗永久卡住。 |
| 修复     | `src/stores/notice.ts`：补 `confirm` 的 404 分支（该任务已不在本人定向范围内 → 摘除该条并放行，不再让用户对着永远 404 的弹窗反复点「收到」）；显式注释空队列语义。`src/api/notice.ts` 补上**此前完全缺失**的 `mine()` 绑定并说明定向口径；`src/types/index.ts` 补 `MyNotice`。               |

| 遗留风险 | **Web 端无「我的通知」页面**（PRD 页面清单里没有该页），`/notice/mine` 目前只有接口绑定与类型，由小程序端消费。若 Web 也要展示全量通知，需先补 PRD 页面（属新增需求，不在本次范围）。                                                                                                        |

### P0-4 · `reviewed` 是终态（交接 A4）—— 含一处**文案纠错**

| 项       | 内容                                                                                                                                                                                                                                                                                                                                                  |
| -------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 根因     | `reviewed` 是状态机终态，教师再提交会 409（此前会静默覆盖已通过内容、撤销审批结论）。功能层面前端已用 `isLockedByReview` 隐藏了填报/提交入口，**问题在文案**：后端 409 文案是「如需修改请**联系教材室驳回后补正**」，但实测**管理员对 `reviewed` 表单调用审核同样 409**（仅 `pending_review` 可审）——文案给出的补救路径不可达，前端若照抄会误导用户。 |
| 修复     | `src/views/teacher/OrderFormView.vue`：`reviewed` 提示改为「已复核通过，本单已定稿，不能再修改或重提」+ 说明「如内容确需调整，请联系教材室按线下流程处理」，**不再复述后端那句不可达的承诺**；提交遇 `STATE_CONFLICT` / `WINDOW_CLOSED` / `CORRECTION_EXPIRED` 时**自动重拉表单状态**（页面状态过期时不再让用户反复撞同一个状态机）。                 |
| 测试结论 | ✅ 场景 A4 实测：教师重提 → **409**；管理员对该 `reviewed` 表单审核 → **409**（终态不可回退，文案矛盾已确认）。                                                                                                                                                                                                                                       |
| 遗留风险 | 后端 409 文案仍写着「请联系教材室驳回后补正」，与本状态机行为矛盾——建议后端修文案（已记入 §五 待办）。                                                                                                                                                                                                                                                |

### P0-5 · 导出/下载硬约束（交接 A6）—— 含一处**交接文档未列出的真实缺陷**

| 项       | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 根因     | ① 同步导出直接回 **xlsx 二进制流**（不是 JSON），必须按 `Content-Type` 分流（已实现，本次复核确认）；② `downloadToken` 只在**任务所有者**的轮询响应里、且任务完成后才有；③ token **在下载开始时即被消费**，复用/过期/文件清理都是 **410**，**原地重试同一 token 必然再失败**；④ **新发现**：`ExportButton` 把轮询与下载端点**写死**为内部 `/api/export-task/{id}`，而供货商必须走物理隔离的 `/api/supplier/export-task/{id}`（`supplierApi.taskProgress/taskDownload` 定义了却无人引用）。 |
| 修复     | `src/components/ExportButton.vue`：轮询/下载端点改为**按角色注入**（新增 `progress` / `download` 两个可选 prop，默认内部端点）；`downloadToken` 缺失时**不发请求**（避免白白浪费一次性机会）并提示重新导出；下载失败不重试同 token。`src/views/supplier/SupplierExportView.vue` 注入供货商专用端点。                                                                                                                                                                                       |
| 测试结论 | ✅ 场景 A6 实测（把 `export.sync_row_threshold` 降到值域下限 100 + 造 111 行已通过明细，强制走异步）：同步分支回 `Content-Type=…spreadsheetml.sheet`；异步分支 `{async:true, taskId, rowEstimate:123}`；轮询 `done` 后下发 token；**首次下载 200（xlsx）→ 同 token 再下载 410 `DOWNLOAD_TOKEN_INVALID`**；缺 token 参数 400。场景 A6-supplier 实测供货商专用端点全流程通过。                                                                                                               |
| 遗留风险 | 见 §三 P2-2（供货商任务经内部端点亦可读）与 §五 待办（供货商受理体缺字段）。                                                                                                                                                                                                                                                                                                                                                                                                               |

### P1-7 · 新增协议错误码 405 / 415（交接 A7）

| 项       | 内容                                                                                                                                                                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### P1-8 · `X-Request-Id` 链路追踪（交接 B 节）

| 项       | 内容                                                                                                                                                                                                                                                                                              |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 根因     | 后端每个响应都回带 `X-Request-Id`，且会**沿用**请求自带的该头；此前前端既不发送也不记录，报障时无法把「用户看到的那次失败」对到后端日志。                                                                                                                                                         |
| 修复     | `src/api/http.ts`：请求拦截器为每个请求生成并带上 `X-Request-Id`；响应侧把它挂到 `ApiError.requestId`（响应未回带时回退到请求自带的 id，**网络中断场景也有 id 可报障**）。`src/utils/monitor.ts` 把 `requestId` 纳入 `ErrorReport` 并在默认上报器输出（保持零依赖，结构化取值不 import 接口层）。 |
| 测试结论 | ✅ 场景 B 实测：响应回带 `7f8ea80f…`；请求自带 `it-probe-fixed-id-001` 被原样沿用。单测覆盖「请求自带头」「响应回带挂到 ApiError」「网络失败回退请求 id」。                                                                                                                                       |
| 遗留风险 | 无。                                                                                                                                                                                                                                                                                              |

### P0-9 · 联调新发现：JSON body 时间格式与文档不符（交接文档未列）

| 项       | 内容                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 根因     | **实测确认的格式不对称**：`API.md §1.1` 称「入参（body/query 的 `LocalDateTime`）一律 `yyyy-MM-dd HH:mm:ss`」，但 **JSON body 只接受 ISO-8601（`yyyy-MM-ddTHH:mm:ss`）**，传空格格式返回 400 `PARAM_INVALID`；而 **query 参数相反**（`/api/admin/audit` 的 `startAt/endAt` 只接受空格格式，传 `T` 反而 400）。前端 `el-date-picker` 的 `value-format` 是空格格式，且该值**直接**发给接口 —— 即「学期窗口设置 / 新建学期 / 延长窗口」这几个功能在后端按文档实现的前提下**必然 400**。 |
| 修复     | `src/utils/format.ts` 新增唯一转换点 `toWireDateTime()`（picker → body 的 ISO）与 `toPickerDateTime()`（ISO → picker 回填，含截掉微秒）；`src/api/semester.ts` 的 `create` / `update` / `setWindow` / `extendWindow` 统一转换；`src/components/SemesterLifecyclePanel.vue` 回填时转换，并补 `watch(props.semester.id)` 避免切换学期时残留上一份时间。                                                                                                                                |
| 测试结论 | ✅ 联调实测：空格格式 `PUT /api/admin/semester/{id}/window` → **400**；ISO 格式 → **200**。`POST .../window/extend` 同。query 侧 `audit?startAt=2026-01-01 00:00:00` → 200，`T` 格式 → 400。单测 `tests/unit/format.spec.ts` 固化两种转换与互逆性。                                                                                                                                                                                                                                  |
| 遗留风险 | 后端 `API.md §1.1` 的表述与实现不符，建议改为「body 用 ISO-8601、query 用空格格式」，否则下一个接入方仍会踩（已记入 §五 待办）。                                                                                                                                                                                                                                                                                                                                                     |

## 三、联调中发现的后端契约偏差（供后端参考）

脚本 `npm run test:api` 会把下列结论写进报告的「联调发现的契约偏差」章节。

| 级别 | 问题                                       | 说明                                                                                                                                                                                                                                                                                                                                                                                                  |
| ---- | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| P0   | JSON body 时间格式与文档不符               | 见 P0-9。文档说空格，body 实际只认 ISO 的 `T`；query 又反过来只认空格。                                                                                                                                                                                                                                                                                                                               |
| P1   | 名单导入会把班级人数刷新为导入行数         | `POST /api/admin/user/import?role=student` 导入 N 行后，该班 `school_class.student_count` 被置为 N。而班级人数是教师填报 `QTY_RANGE` 的数量上限来源——**导入一份 1 行名单会把该班填报上限压到 1**（实测 30→1，随后教师提交 `quantity=2` 立即 400）。                                                                                                                                                   |
| P1   | `reviewed` 终态与错误文案自相矛盾          | 教师重提的 409 文案让人「联系教材室驳回后补正」，但管理员对 `reviewed` 表单审核同样 409——补救路径不可达。                                                                                                                                                                                                                                                                                             |
| P1   | 学期 `activate` / `archive` 不可逆且无回滚 | `activate` 会把当前 active 学期置为 `archived`，而归档学期**不可再激活**（409「仅 draft 学期可激活」）；`archive` 又要求学期处于 `active`。即切换学期后**无法通过接口回到原状态**（唯一恢复手段是直接改库）。本次联调已复现并手工修复了演示库（把种子学期 1 的 `active_status` / `window_status` / `channel_open` 改回）。因此联调脚本**不再执行 activate/archive 的 happy path**，只断言状态机门禁。 |
| P2   | 权限门先于归属校验                         | 无权限角色得到 **403**，有权限但非本人得到 **404**（`/batch/{id}`、`/supplier/export-task/{id}`）。前端不能靠 403/404 差异判断资源是否存在，但需按角色区分提示。                                                                                                                                                                                                                                      |
| P2   | 供货商导出受理体缺 `async` / `rowEstimate` | 异步时 `POST /api/supplier/export` 只回 `{taskId}`，而 `API.md §3.10/§3.13` 承诺 `{taskId, async:true, rowEstimate}`；同场景 `/api/admin/export/orders` 回完整三字段。前端以 `Content-Type` 分流且只读 `taskId`，**当前不受影响**，但类型声明与契约不一致。                                                                                                                                           |
| P2   | 供货商任务经内部端点亦可达                 | 文档称供货商任务只经 `/api/supplier/export-task/{id}` 可达（物理隔离），实测**任务所有者**经内部 `/api/export-task/{id}` 同样可读可下载（按所有者维度判定，未按角色隔离）。非所有者仍是 404，故不构成越权，但与「物理隔离」的表述不符。                                                                                                                                                               |
